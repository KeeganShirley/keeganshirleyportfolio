Case Study · Serverless Architecture

Three-Tier Web Application

A robust, scalable three-tier web application built entirely on serverless AWS resources to minimize operational overhead. Visitors can query a database and retrieve user data through a clean presentation, logic, and database layer split.

Amazon S3CloudFrontAPI GatewayLambdaDynamoDB
Objectives

Functional Requirements

  • ✓ Fetch user data on request from the website's visitor
 

Non-Functional Requirements

  • ✓ 99.9% uptime availability
  • ✓ Handle up to 10,000 concurrent users without performance degradation
  • ✓ Response time under 3 seconds
Architecture

Workflow & Draft Architecture

  1. 1 Presentation: static website on S3, served through a CloudFront distribution
  2. 2 Logic: Lambda function behind an API Gateway to process requests
  3. 3 Database: DynamoDB table populated with user data
  4. 4 Integration: Lambda granted read-only access to DynamoDB; website wired to API Gateway
  5. 5 Validate end-to-end functionality
Building It

Presentation, logic, and database — wired together

Presentation layer. I used Microsoft Copilot to generate simple web files, uploaded them to an S3 bucket, and put a CloudFront distribution in front of it — setting Origin Access Control so only CloudFront (not the public) could reach the bucket's objects, with index.html as the default root object.

Locking down the bucket. I scoped the S3 bucket policy to accept requests only from that specific CloudFront distribution, then confirmed the distribution's URL was serving the site correctly over HTTPS.

LOGIC LAYER

Programming the Lambda function

This function fetches user data from a DynamoDB table when a visitor enters a user ID on the site. It receives the ID via a query string parameter, initializes a DynamoDB client, issues a Get command against the UserData table, and returns the matching item — or an error message if nothing is found.

Creating the API Gateway. I built a REST API, configured a GET method connected to the Lambda function, enabled CORS to keep cross-origin requests secure and functional, and deployed a production stage.

Creating the DynamoDB table. I set the partition key to userID so the table queries return all data tied to a given ID, then added test attributes to validate the schema.

LEAST PRIVILEGE

Assigning permissions to the Lambda function

Applying the principle of least privilege, I granted the RetrieveUserData function read-only access to DynamoDB — it only needs to retrieve data, never write or modify it. After this, the logic and database layers were fully integrated and returning data correctly.

INTEGRATION

Integrating the website with API Gateway

I pointed the front-end JavaScript at the API's invoke URL so that pressing "Get User Data" triggers the right request — connecting the presentation layer to the logic layer end to end.

VALIDATION

Validating the application

With every layer wired together, I tested the full flow: enter a user ID, press "Get User Data," and the app pulls the matching record straight from DynamoDB through the API.

Results

Requirements Evaluation

  • ✓ Fetch user data — the button on the landing page triggers API Gateway, which invokes Lambda to retrieve the record from DynamoDB and return it.
  • ✓ Uptime — based on AWS service SLAs, the stack projects at least 99.95% monthly uptime, ahead of the 99.9% target.
  • ✓ Concurrency — the serverless architecture is designed to handle 10,000 simultaneous users without degradation.
  • ✓ Response time — testing samples stayed just under 2 seconds, comfortably inside the 3-second budget.
